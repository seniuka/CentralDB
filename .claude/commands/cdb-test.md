# /cdb-test

Inputs: $ARGUMENTS. Unit name and a non-production target instance.

Preconditions:

- `src/` files exist for the unit. Otherwise stop and name the Develop command.
- Target guard: the instance must be in `docs/nonprod-targets.md` and must not look like a production listener. If the check fails, stop and print: "Target refused. To proceed, type: CONFIRM-TARGET: <exact name>". The confirmation must be typed by the user in this session.
- Pester version: run `Get-Module -ListAvailable Pester`. The scaffold session found only Pester 3.4.0 on the author's workstation. Tests are written for Pester 5. If no 5.x module is installed, stop and raise a DECISION: Pester 5 must be provided from the UNC PSRepository. Do not install anything from the internet.

Steps:

1. Parse tests (always run, no server needed): PowerShell parse on 5.1 and 7.2+, and offline T-SQL parse, as in the `cdb-collector-pattern` skill, section "Parse checks".
2. Generate Pester tests in `Tests/Pester/<Unit>.Tests.ps1`: parameter contract (`[DbaInstanceParameter]`, `-Apply` present, default off), report-only behavior (no write when `-Apply` is absent), result contract fields, throttled parallel path and the 5.1 fallback, error capture into the run log.
3. Generate T-SQL assertion tests in `Tests/Sql/<Unit>.assert.sql`: object existence, key and index presence, partition function boundaries, retention settings, temporal and masking metadata, reconciliation queries returning zero differences. Plain assertion scripts are the default. tSQLt is a new dependency, so propose it in chat first and wait.
4. Test data is synthetic and generated by the test, never copied from any inventory. Never put Protected C names, hosts or counts into a fixture.
5. Run the tests only against the named guarded target, and only after the user approves the PowerShell prompt. Report-only paths run first. Paths that need `-Apply` run only if the user typed `-Apply` in this session.
6. Record results in `docs/rebuild/test-results/<unit>.md`: date, target role (not the name if the name is sensitive), passed, failed, skipped, and reasons.
7. Document the tests in `docs/TESTING.md` (append a section for the unit, do not overwrite).

Exit check: tests exist and parse; results are recorded; zero failures, or each failure is listed with an owner and the unit is marked blocked.

Next: `/cdb-quality <unit>`.
